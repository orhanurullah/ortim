# M2 — PWA + Wrapper (Capacitor)

> Pick when an existing web app needs a thin mobile presence, not a true mobile experience.

## When to use
- Mature React/Vue/Svelte web codebase exists, proven and shipped
- Mobile is a wrap-and-distribute concession, not the primary product surface
- App-store presence is the goal (discoverability, payment, auth) more than native UX
- Hardware needs are minimal: camera/photos, files, basic share

## When NOT to use (BLOCKED)
- iOS push notifications required — Web Push on iOS is unreliable enough that Apple's own docs caveat it
- BLE access on iOS — not available in WKWebView at all
- Truly native UX expected by users — M1 (Flutter) gives more for similar effort
- Performance-sensitive workloads — every interaction routes through a WebView

## Architecture
Existing web app + Capacitor (or Cordova; Capacitor preferred). One web codebase, two thin native shells (iOS Xcode project, Android Gradle project).

## Canonical Tech Stack

| Layer | Choice |
|---|---|
| Web | Existing React / Vue / Svelte app (no rewrite) |
| Wrapper | Capacitor 5.x |
| Native plugins | Capacitor official plugins first; avoid community plugins for core paths |
| Build | Web build → `cap sync` → Xcode/Gradle build |
| Distribution | TestFlight + Google Play Internal Testing |
| Storage | localStorage / IndexedDB (web) + Capacitor Preferences for native-side bits |
| Auth | Reuse web session; Capacitor Browser plugin for OAuth flows |

## Layout

```
project/
├── web/                  # existing web app (React, Vue, Svelte) — UNCHANGED
├── capacitor.config.ts
├── ios/                  # generated by `npx cap add ios`
│   └── App/
└── android/              # generated by `npx cap add android`
    └── app/
```

The point is: `web/` doesn't need a fork. Mobile-specific code paths (e.g. native share sheet) wrap `Capacitor.isNativePlatform()` checks behind feature toggles.

## Cross-Cutting
- **Status bar, splash, safe areas**: configure in `capacitor.config.ts`; do not reinvent.
- **Deep links**: Capacitor's App plugin + universal links / app links per platform.
- **Camera / files**: official Capacitor plugins — one well-maintained code path.
- **Performance**: WebView memory ceiling on Android < 256MB on low-end. Profile aggressively.

## Test Strategy
- Existing web tests still cover most logic.
- Add Capacitor-specific smoke tests: app launches, can navigate to first route, can call one native plugin.
- Manual device pass per release on representative iOS + Android device.

## CI
- Reuse web CI for the build artifact.
- Add a separate job that runs `npx cap sync` and validates Xcode + Gradle build (no need to actually distribute on every PR).
- Distribution lane runs on `main` only.

## Risks
| Risk | Impact | Mitigation |
|---|---|---|
| iOS WKWebView gaps surface late | App-store rejection or critical user flow broken | Maintain a "native required" feature inventory; M1 fallback decision documented |
| Capacitor plugin abandonment | Build breaks on next OS update | Pin to Capacitor official plugins; budget time for replacement |
| Performance ceiling | Users perceive app as "websitey" | Set numeric perf targets; abandon M2 if missed twice in a row |
| App-store policy updates | Wrappers in grey area periodically | Monitor App Store / Play policy changes |

## Migration paths
- **M2 → M1 (Flutter)** — common. Trigger: critical native gap or perf ceiling. Approach: rewrite mobile-only; keep web codebase as-is; share backend.
- **M2 → M0 (native)** — rare; only if M1 is also rejected (e.g. very specific hardware needs).
- **M2 → web-only retreat** — also acceptable; sometimes the right answer is "we don't need an app yet."

## Anti-patterns
1. Adding too many community plugins — each one is a long-term liability.
2. Building mobile-specific UI in the web codebase — defeats the purpose; either keep it web-shaped, or move to M1.
3. Treating WebView as a sandbox — it can leak across page reloads; always handle auth refresh explicitly.
