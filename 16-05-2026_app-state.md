 1. Ortim için Docker dosyası

  Bugünkü kullanıcı profili Docker'a uymuyor

  ortim doctor çıktısına bak — required check'ler Python 3.11+, workspace yazma izni, audit dir, L1 principles
  dosyaları. Recommended check'ler Git, API key'ler, Node/Cargo/Flutter. Bu sahibi olduğu makinenin dev environment'ını
  yöneten biri. O kişi için Docker friction — docker run -v $PWD/workspaces:/work ortim demo yazmak ortim demo'dan kötü
  UX.

  Docker'ın gerçek değer ürettiği üç senaryo var

  1. CI runner: GitHub Actions / GitLab CI job'unda Ortim koşturmak istemek. Bugün YAML'da pip install -e . + 5 binary
  kurulumu var. uses: ortim/run-action@v1 veya image: ortim/cli:latest çok daha temiz. Bu, CI/CD pipeline'larında AI dev
   pipeline kullanımının ilk gerçek talebi olur.
  2. Air-gapped / regulated enterprise: Banka, savunma, sağlık. Pip install internet gerektirir, Docker tarball offline
  transfer edilebilir. Bugünkü kullanıcı buralarda değil ama yarın olabilir.
  3. Fresh machine onboarding: PyPI publish öncesi pip install ortim çalışmıyor. Docker docker run ortim doctor ile
  0-to-running 30 saniye. PyPI shipped olduktan sonra bu değer kaybolur.

  Teknik komplikasyonlar göz ardı edilemez

  - Image size problemi: Ortim subprocess olarak npm, pytest, flutter, cargo, go çağırıyor. Tüm runtime'ları imaja
  koyarsan 4-6GB. Layered approach gerek: ortim/cli:python-only, ortim/cli:web (Node+npm), ortim/cli:full. Bu
  maintenance + CI matrix.
  - Docker-in-Docker (DinD): Worker bir npm install çağırırsa, container içinden başka bir container... DinD security
  implications + setup complexity. Alternatif: volume mount + host'ta runtime. Ama bu Docker'ın "self-contained"
  iddiasını çürütür.
  - Workspace volume mount: workspaces/ host filesystem'de durmalı (kullanıcı inspect edecek). -v
  $PWD/workspaces:/workspaces zorunlu. Windows path resolution sorunu burada başlar.

  Önerim ve sebep

  Şimdi hayır, Q3-Q4 2026'da yeniden değerlendir. İlk öncelik PyPI publish (pip install ortim). Bu, "fresh machine"
  kullanıcısının %80'ini kapatır. Docker, %20'lik enterprise/CI segmenti için. SQ-4 (hedef kitle) cevaplanmadan Docker'a
   yatırım, bilinmeyen kullanıcı için template yapmak — memory'deki "talep gelmeden tier matrix expand etme" disiplinin
  aynı uygulaması.

  Hazırlık olarak yapılabilir: docker/Dockerfile.draft (untracked, isim taslak) ve docker/README-draft.md repo'da dursun
   ama README'den link verme, PyPI publish sonrası gerçek talep gelirse 4-6 saatte production'a alınır.

  2. Üretilen projelere Docker dosyası

  "Her zaman Docker" antipatterni neden tehlikeli

  ortim demo'nun ürettiği T2 BaaS todo CLI workspace'inde 7 dosya var (PRD/RFC/DAG/intent + 3 modül stub). Eğer her
  projeye default Dockerfile + .dockerignore + docker-compose.yml eklersek, artefakt sayısı 2 katına çıkar ve
  kullanıcının %60'ı bu dosyalara dokunmaz (T0 single-file CLI deploy etmez, hobi todo app'i lokal çalışır).

  Daha kötüsü: Worker LLM'i artık Dockerfile da yazıyor. Her task çağrısında ekstra ~200-500 token. 12-task projede
  ~3-6K extra token ($0.003-0.006 ekstra DeepSeek). Marjinal görünüyor ama "kim bunu kullanıyor?" sorusuna ekleniyor —
  kullanıcının %80'i sadece local çalıştırırken bu maliyet ödeniyor.

  cloud-only.

  Setup friction altımıza yatırılmıyor

  Local LLM kullanıcısı için onboarding adımları:
  1. Ollama install (~200MB)
  2. Model pull — ollama pull qwen2.5:32b (~20GB) veya qwen2.5-coder:32b
  3. RAM/VRAM: 32B model GGUF Q4 quantize ile ~20GB RAM. Mac M2 Max veya 24GB+ GPU.
  4. Latency: M2 Max'te 30B model ~8-15 token/sec. Cloud DeepSeek ~80-120 t/s. Demo $0.01 maliyet → local'de 5-10x daha
  yavaş.

  Bu kullanıcı tabanı dar ama gerçek. KVKK / GDPR ağır endüstri, defense contractor, off-grid researcher.

  Hibrit pattern doğru cevap

  Per-role routing zaten implemented (memory: client_for(role)). Local LLM eklendiğinde kullanıcının .env'sinde:
  BABEL_PROVIDER=ollama
  BABEL_MODEL=qwen2.5:7b
  INTENT_ANALYST_PROVIDER=ollama
  ARCHITECT_PROVIDER=anthropic     # cloud for critical
  REVIEWER_PROVIDER=anthropic
  WORKER_PROVIDER=ollama
  WORKER_MODEL=qwen2.5-coder:32b

  Bu setup tipik bir proof-point'i ~$0.001-0.003'e indirir (sadece Architect + Reviewer cloud). Privacy-sensitive parça
  (kullanıcı kodu) local kalır.

  Riskler honest

  1. Yanlış vaadlerden kaçınmak gerek. "Tamamen offline" demek ama gerçekte Architect cloud'da → kullanıcı KVKK
  uyumluluk sözüne güvenirse hukuki risk. Belgeleme net olmalı: "Babel + Worker local; Architect + Reviewer cloud
  (önerilir/zorunlu)".
  2. Model kalite varyans. 32B Qwen-Coder bugün iyi, 6 ay sonra daha iyi olur. Ama Q4 quantize çıktısı F16'dan kalitatif
   düşüktür. Worker output parse-fail oranı artar → retry ile maliyet eşitlenir.
  3. Test stratejisi. Local LLM ile real-LLM E2E fixture'larını yeniden capture etmek gerekir — Qwen output'u DeepSeek
  output'undan farklı olur, snapshot test'ler kırılır.

  Önerim ve sebep

  Ship et — provider olarak, beklentileri çerçeveleyerek. Tahmin: 6-8 saat.
  - Provider entry + env var contract: 2h
  - client_for(role) ile per-role routing dokümante edilmesi: 1h
  - Quality-tier matrix documenter (docs/local-llm.md): 1h
  - 3 yeni test: provider abstraction, env var fallback, hata mesajları: 2h
  - Bir live proof-point Qwen-Coder ile (T0/web Python CLI brief'i): 1-2h

  Bu, Item 23 (provider fail-loud) discipline'i ile birlikte ship edilirse kullanıcı kritik rolde yanlış provider
  kullanıyorsa stderr uyarı alır.

  Pazarlama değeri yüksek — "AI dev tool that you can run fully local" başlığı startup/indie geliştirici segmentinde
  adoption argümanı. SaaS Cursor/Copilot Workspace bunu yapamaz; Ortim'in open-source mimarisi yapabilir.

  4. PRD → MVP yapısı yeterli mi?

  Mevcut akışın anatomisi

  Şu an pipeline:
  Brief
    → Babel (intent.json structured)
    → IntentAnalyst (must_have_features + nice_to_have + non_goals + open_questions)
    → [optional M2 dialog refinement]
    → PRDAnalyst (markdown PRD)
    → G1 review
    → Architect Call 1 (GoldenPathInputs — tier inputs)
    → tier scorer (deterministic T0-T6)
    → Architect Call 2 (RFC §1-§16 markdown)
    → G2 review
    → Orchestrator (TaskDAG)
    → Worker × N

  PRD şeması (memory'den): goal, target_users, must_have_features, nice_to_have_features, explicit_non_goals,
  constraints, inferred_compliance, inferred_scale, open_questions.

  "MVP" yapısal olarak yok

  PRD'de must_have_features bir flat list. Bu listenin tamamı RFC'ye giriyor, RFC'nin tamamı DAG'a giriyor. "MVP'de ne,
  sonraya ne kalıyor" sinyali hiçbir yerde yok.

  Pratikte ne oluyor: Architect Call 1 implicit olarak "smallest viable" picks (kullanıcı small/solo/low diyorsa scale
  küçük tutar). Bu IMPLICIT — kullanıcı şunu söyleyemez:
  - "Auth'u MVP'de tut ama sosyal login Phase 2'ye"
  - "CRUD MVP, tagging Phase 2"
  - "Web MVP, mobile companion Phase 3"

  Daha kötüsü: kullanıcı nice_to_have_features listesine bir şey koysa bile, bu features RFC'ye girmiyor mu? Net değil.
  Architect prompt'una bakmadan söyleyemem.

  Endüstri standartlarına karşı boşluk

  Yeterli MVP pipeline şunları taşır:
  - MoSCoW prioritization: Must / Should / Could / Won't have (RFC 2119'dan beri standart). Ortim'in must_have_features
  sadece "Must"; geri kalan 3 yok.
  - Acceptance criteria gates: Her feature'ın "MVP done" tanımı ayrı, "production done" tanımı ayrı.
  - Phase planning: MVP → Phase 2 → Phase N. Each phase as a release.
  - Risk/uncertainty markers: Hangi feature bilinmiyor, hangi feature bilinen tasarım problemi içeriyor. Ortim'de
  open_questions var ama feature'a bağlanmıyor.
  - Effort estimation: T-shirt sizes (S/M/L/XL) veya story points. Ortim'de sadece estimated_tokens (LLM cost proxy).
  - Alternative solutions analysis: "X için: Option A in-memory, Option B SQLite, Option C cloud KV. Tercih: B çünkü..."
   Bu RFC'de yer alıyor mu? Bilinmiyor; prompt'a göre değişir.

  Discovery cap zayıf

  Memory'deki proofpoint48'in intent.json'unu hatırla:
  {
    "goal": "Build a modern web-based todo application.",
    "must_have_features": [
      "task creation",
      "task listing",
      "task completion marking",
      "task deletion",
      "local data persistence"
    ],
    "open_questions": []
  }

  open_questions: [] boş. Demo run'da da boş çıktı. Bunun sebebi: brief uzun ve detaylıydı, Babel/Analyst soracak şey
  görmedi.

  Ama gerçek dünyada user "CRM istiyorum" derse bu nasıl çözülür? Şu an Architect overconfident bir PRD üretir çünkü:
  - Babel "muhasebeci için CRM mi, satış için CRM mi?" sormuyor
  - IntentAnalyst features çıkarımı yapıyor ama temel sorular sormuyor ("kullanıcı sayısı? data hacmi? integrate
  edilecek sistemler?")
  - M2 dialog mode bu sorular için kanalı var ama Analyst aktif olarak sormuyor — kullanıcı ortim refine çağırırsa belki

  Bu agent passivity problemi. İyi bir senyör analyst kullanıcıyı 30dk grill eder; Ortim'in Analyst'i 3 LLM call'da
  hallediyor.

  Decomposition granularity sorunu

  Orchestrator task düzeyinde duruyor. Bir task "Implement TaskRepository with CRUD operations" gibi 4-9 acceptance
  criteria içerebilir. Worker bu task'ı tek LLM call'da yazar → internal decomposition silent. 200-line file produce
  edebilir.

  Memory'de "two-shot Worker = pragmatic 80%" denmiş ama uygulanmamış. Method-level granularity yok. Bir TaskRepository
  task'ı:
  - Constructor
  - createTask
  - getAllTasks
  - completeTask
  - deleteTask

  5 method, hepsi tek call'da. Bir tanesi yanlış olursa task tüm dosyayı yeniden yazıyor (operation: overwrite). Bu
  maliyetli ve hata-eğilimli.

  Concrete eksik mekanizmalar — beşi

  1. PRD schema'ya mvp flag:
  class Feature(BaseModel):
      description: str
      priority: Literal["must", "should", "could", "wont"]  # MoSCoW
      phase: int = 1                                          # 1=MVP, 2+=later
      rationale: str = ""
      risk_markers: list[str] = []
  2. MVP_SCOPE_LOCKING state — G1 öncesi yeni bir HITL state. Kullanıcı PRD draft'ı görüp her feature'a MoSCoW priority
  ve phase atar. Auto-suggestion verilebilir ama lock kullanıcıda.
  3. RFC iki-katmanlı modül:
  ## §7 Module Breakdown (MVP)
  | Module | Phase 1 (MVP) | Phase 2+ |
  |---|---|---|
  | task | CRUD | tagging, search |
  | ui | basic list/form | drag-drop, themes |
  4. DAG'da phase tagging: Her TaskSpec'e phase: int field'ı. ortim run-all --phase 1 sadece MVP task'larını koşturur.
  5. Alternative solutions section: RFC §4 Tech Stack altında "Considered alternatives" subsection — Architect bilinen
  seçenekleri enumerate eder, hangisini niye seçtiğini yazar. Bu existing PRD/RFC template'lerinde yok.

  Mevcut yapının handa ettiği yerler — adil olalım

  Yetersiz dediğimiz şeyler küçük projeler için yeterli. proofpoint48 (todo app + tagging extension) MVP-explicit
  olmadan da çalıştı, T-007/T-008 DONE, T-009 doğru HITL. Bu 5-10 task ölçeğinde sistem işliyor.

  Sorun 30+ task'lık projeler, çoklu stakeholder ihtiyacı, faz planlama gereken durumlarda başlıyor.

  Önerim ve sebep

  Şu an yeterli değil — ve bu sistemin en kritik kısa-vade eksikliği. Effort tahmini:

  ┌───────────────────────────────────────────────────────────────────────┬──────┐
  │                                 Adım                                  │ Efor │
