# M3.1 — `ortim extend` (iterative development on shipped projects)

**Status:** Design draft v0 — 2026-05-14. To be locked after one user-review pass.
**Effort estimate:** ~3-5 days across **2 sub-phases** (M3.1.0 foundation + M3.1.1 delta DAG validation). M3.1.2 drift detection + M3.1.3 multi-iteration are follow-on items.
**Closes:** Backlog item 5 root ("Proje extend yok — her brief baştan başlıyor"); deferred from original M3 scope.
**Built on:** M1 brownfield codebase reader + M2 LockedStack + M4 cross-task export visibility.

---

## 1. The problem M3.1 solves

Today, after `ortim run-all` finishes and project state hits `DONE`, the workspace is final. To add a feature like "add tagging to tasks" to a shipped todo app, the user has to:

1. Start a **new project** with `ortim new "todo app with tagging"`.
2. Walk the full Babel → IntentAnalyst → StackAnalyst → PRDAnalyst → Architect → Orchestrator pipeline from scratch.
3. The new project's DAG will re-emit T-001 through T-005 covering the same modules. The Worker can't reference the original project's code because they're in separate workspaces.
4. User either accepts duplicate work (cost + time) or manually copies files between workspaces (defeats the purpose).

The brownfield reader (M1) solves the "existing codebase plug-in" case for projects the system didn't build. M3.1 solves the same case for projects the system **did** build, where we already have the full audit chain, LockedStack, RFC, and DAG — far more context than M1's external scan.

**Vision:** `ortim extend <id> "<feature brief>"` produces a delta PRD section + delta RFC section + delta task DAG, with new tasks that reference existing DONE-task exports (M4 already plumbs the visibility). The existing pipeline does the rest.

## 2. Locked design decisions

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Workspace strategy | **In-place delta.** Same workspace; PRD/RFC/task_dag get appended deltas. Existing DONE tasks stay DONE. | Sub-project (sibling workspace) would duplicate state machine + audit chain + force users to track parent-child relationships. In-place keeps "the project" as the unit. |
| 2 | PRD/RFC delta strategy | **Append a new section per extend cycle.** PRD gains `## Extension <N> — <feature title>` after the original sections; RFC gains the same. Original sections untouched. | Re-drafting the full PRD/RFC on every extend re-opens already-settled decisions. Append-only is honest about what changed. |
| 3 | LockedStack mutability | **Locked forever after first STACK_DIALOG lock.** `ortim extend` cannot change the stack. Adding a library is a key_libraries amendment (handled separately via M3.2 if it ever ships). | Stack change mid-project breaks the M4 cross-task contract. If the user genuinely needs a new stack, they start a new project (which is rare in practice). |
| 4 | Task ID numbering | **Continuous.** First extend's tasks start at the next free integer after the highest existing task ID. Initial DAG: T-001…T-005; first extend: T-006, T-007; second extend: T-008. | Block numbering (T-101 for extend 1, T-201 for extend 2) is more transparent but forces explicit per-cycle metadata. Continuous numbering keeps task_status.json + git branch names simple; the audit log knows which extend cycle a task belongs to. |
| 5 | Re-emitting HITL gates | **G1 (PRD) and G2 (RFC) fire again for each extend cycle.** The user must approve the delta PRD section and delta RFC section before TASKS_GENERATING. G3–G7 fire as normal during execution. | The delta is new decision surface; skipping G1/G2 would re-introduce "approval fatigue is the bug, not the gates". |
| 6 | State machine path | **`DONE → EXTEND_DIALOG → EXTEND_PRD_DIALOG → EXTEND_PRD_APPROVED → EXTEND_RFC_DRAFTING → EXTEND_RFC_APPROVED → TASKS_GENERATING → EXECUTING → DONE`** (loops back to DONE). New states reuse existing transition discipline. | Adding states is verbose but explicit; trying to reuse `INTAKE_DIALOG`/`PRD_DIALOG` directly conflates "fresh project" with "extending project" — they should be visibly different in `ortim status`. |
| 7 | Git branch strategy | **`task/T-NNN` continues.** Existing T-001..T-005 already merged into main; T-006+ branches off main. No `extend-N/` prefix. | Branch namespace stays flat; commit history shows the extension story by chronology. |
| 8 | Audit event discrimination | **New event types: `extend_initiated`, `extend_prd_delta_drafted`, `extend_rfc_delta_drafted`, `extend_dag_appended`.** Existing per-task events (`worker_output_ok`, etc.) are unchanged. | Filtering "what did extend cycle N do" needs explicit event types. |
| 9 | Cross-task visibility | **All previously-DONE tasks' exports are visible to new extend tasks (M4 logic unchanged).** New extend tasks can import from any existing DONE module. | M4 already enumerated DONE tasks for cross-task export visibility; extend tasks are just "later DONE tasks the next set will reference". No change needed. |
| 10 | Reviewer rubric for extend tasks | **Same rubric, same `criteria_verdicts` discipline.** Acceptance criteria for extend tasks come from the delta RFC, scoped to the new modules or extension points. | The rubric (Phase 0) doesn't know or care whether a task is initial or extension — it sees `module_scope` + criteria + code, same contract. |

**Deferred to M3.1.2 / M3.1.3 / later:**
- **Drift detection** (M3.1.2): What if the user manually edited the workspace between `DONE` and `extend`? Current design assumes the workspace's code is still what the original DAG produced. Drift handling = separate item.
- **Stack amendment** (M3.2 if ever): adding a single library to LockedStack without re-running STACK_DIALOG. Not in M3.1.
- **Refactor / breaking change extensions**: e.g. "rename TodoService to TaskService everywhere". This needs cross-module rewrite that the current M4 cross-task model doesn't support cleanly. Out of scope.
- **Extension rollback**: undo an extend cycle. Not in M3.1; if user wants to roll back, they revert git commits and reset task_status.json manually.

## 4. Schemas

```python
# runtime/extend/schema.py (NEW)

@dataclass(frozen=True)
class ExtensionIntent:
    """User-supplied delta brief, structured by Babel. Mirrors
    StructuredIntent shape but is parented to an existing project_id."""
    parent_project_id: str
    cycle: int                    # 1 for first extend, 2 for second, ...
    goal: str
    must_have_features: list[str]
    explicit_non_goals: list[str]
    constraints: list[str]


@dataclass(frozen=True)
class DagDelta:
    """The new tasks appended to task_dag.json by an extend cycle.
    Existing tasks are NOT modified."""
    cycle: int
    new_tasks: list[TaskSpec]     # task_ids must NOT collide with existing
    starts_from_task_id: str      # e.g. "T-006" — the first new ID
```

`task_dag.json` schema gains a `extensions: list[DagDelta]` field (default `[]` for projects that have not been extended).

## 5. Contracts

### 5.1 `ExtenderAgent`

```python
class ExtenderAgent:
    """Produces a delta PRD section + delta RFC section from a new feature
    brief, given the existing project's locked artifacts."""

    def draft_delta_prd(
        self,
        feature_brief: str,
        existing_intent_md: str,
        existing_prd: str,
        locked_stack: LockedStack,
        cycle: int,
        project_id: str,
    ) -> str:
        """Returns the markdown section to be appended to PRD.md as
        `## Extension <cycle> — <feature title>`. The section follows
        the PRD template structure (Goal / Users / Stories / AC /
        Constraints) but scoped to the delta."""

    def draft_delta_rfc(
        self,
        delta_prd_section: str,
        existing_rfc: str,
        existing_codebase_summary: CodebaseSummary,
        locked_stack: LockedStack,
        cycle: int,
        project_id: str,
    ) -> str:
        """Returns the markdown section to be appended to RFC.md as
        `## Extension <cycle> — <feature title>`. Constrained to the
        same LockedStack as the parent; modules either extend existing
        (`task-service`) or introduce new (`tagging/`). Cross-task
        exports from existing DONE tasks are listed verbatim so the
        delta RFC's Module Breakdown can reference them."""
```

### 5.2 Orchestrator extension

```python
# runtime/agents/orchestrator.py

def generate_dag(
    self,
    rfc_text: str,
    project_name: str,
    project_id: str,
    prior_dag: TaskDAG | None = None,        # NEW for M3.1
    extend_cycle: int | None = None,         # NEW
) -> TaskDAG:
    """When `prior_dag` is provided, new task IDs MUST start at
    `prior_dag.max_task_id() + 1`. New tasks may declare dependencies on
    existing DONE tasks. The Orchestrator prompt receives the prior
    task list as context."""
```

## 6. CLI surface

```
ortim extend <project_id> "<feature brief>"
    # Triggers DONE → EXTEND_DIALOG; runs Babel on the brief; ExtenderAgent
    # produces delta intent + delta PRD section; HITL G1 (extended);
    # ExtenderAgent.draft_delta_rfc; HITL G2 (extended); Orchestrator
    # generate_dag(prior_dag=...); TASKS_GENERATING → READY.

ortim extend <project_id> --status
    # Show extension cycle history: cycle N | feature title | task IDs
    # added | DONE/AWAITING/FAILED counts.

ortim extend <project_id> --rollback <cycle>
    # NOT IN M3.1. Out of scope.
```

Existing commands (`run`, `run-all`, `execute`, `status`, `tasks`, `gates`, `advance`) work unchanged. `run-all` will see new PENDING tasks (T-006+) and process them; DONE tasks remain DONE.

## 7. Downstream coverage scan

> **Per the new item template discipline:** widening an agent's autonomous range OR introducing new state transitions OR new task IDs requires explicit downstream coverage.

| Layer | Needs widening? | What |
|---|---|---|
| **State machine** | ✅ Yes | 7 new states + 8 new transitions + 2 HITL gates |
| **Project schema** | ✅ Yes | `extensions: list[DagDelta]` field on `task_dag.json` schema |
| **CLI router** | ✅ Yes | `extend` subcommand; `--status` and (future) `--rollback` flags |
| **Orchestrator DAG validator** | ✅ Yes | Two new rules: (a) new task IDs > max existing; (b) new task `module_scope` ∈ (existing ∪ delta) modules |
| **`ortim status` rendering** | ✅ Yes | Must surface extension cycle, last-touched cycle, in-flight extension |
| **`ortim tasks` rendering** | ✅ Yes | Group by cycle (initial / extension 1 / extension 2 / ...) — visual delta |
| **`ortim gates` rendering** | ✅ Yes | G1/G2 may refer to extended cycle; output should disambiguate |
| **Audit schema** | ✅ Yes | New event types listed above |
| **`runtime/codebase/prior_tasks.py`** | ❌ No — already handles arbitrary DONE task discovery | Same enumeration approach used by M4 |
| **Bootstrap** | ❌ No — bootstrap is idempotent + only runs on first `tasks_ready` transition | Extend cycles don't re-bootstrap |
| **`_NPM_DEP_REGISTRY` / `_FRAMEWORK_PACKAGES`** | ❌ No — LockedStack is unchanged, deps already installed | Same |
| **Reviewer chain** | ❌ No — acceptance criteria come from delta RFC, otherwise same flow | Same |
| **Test runner** | ❌ No — per-task scoping (Item 39b) already module-bounded | Same |
| **Hooks (`pre_commit`, `pre_deploy`)** | ❌ No | Same flow per task |

## 8. Acceptance criteria (binary, per Hard Rule 10)

### M3.1.0 — Foundation

1. `ProjectState.EXTEND_DIALOG` and the 6 sibling states exist in `runtime/orchestrator/state_machine.py`; tests assert `ProjectState.DONE -> ProjectState.EXTEND_DIALOG` is a valid transition.
2. `ortim extend <id> "<brief>"` CLI command exists and produces a non-zero `intent.json` delta in `workspaces/<id>/extensions/cycle_1/`.
3. `ExtenderAgent.draft_delta_prd()` and `.draft_delta_rfc()` exist; given fixture inputs, produce sections that start with `## Extension <cycle> —`.
4. `runtime/extend/schema.py::DagDelta` exists; task_dag.json gains `extensions` field; legacy task_dag.json files load with empty `extensions: []` (back-compat).
5. New audit events emitted: `extend_initiated`, `extend_prd_delta_drafted`, `extend_rfc_delta_drafted`. Existing E2E run (pre-extend) produces zero of these events.

### M3.1.1 — DAG validation + executor integration

6. `Orchestrator.generate_dag(prior_dag=...)` raises `ValueError` if a new task ID collides with any existing ID.
7. `Orchestrator.generate_dag(prior_dag=...)` raises `ValueError` if a new task's `module_scope` is NOT in (existing RFC §7 ∪ delta RFC §7) modules.
8. `run-all` on a project post-extend processes only PENDING tasks; existing DONE tasks stay DONE.
9. New tasks see existing DONE task exports via M4's `collect_prior_outputs` (existing test pinning, no change).
10. **E2E proof-point:** Run `ortim extend 66244246c339 "add tagging to tasks"`. Expect ≤3 new tasks (T-006, T-007, T-008), all first-attempt approved if the planning chain is clean. Cost: ~$0.10.

## 11. Risks

| Risk | Likelihood | Mitigation | Downstream check |
|---|---|---|---|
| **Reviewer over-quotes existing code as "violations"** in delta tasks (e.g. flags an existing import as if Worker emitted it) | Medium | Reviewer prompt already only sees emitted files (`WorkerOutput`), not existing code; M4 cross-task exports are "context for reading", not "code for review". Verify in M3.1.1 E2E. | `agents/reviewer.md` |
| **Existing DONE task imports break** when new module is added (e.g. new task adds `auth/` and existing T-003 needs to import from it — but T-003 already DONE) | Low-Medium | Out of scope by design: M3.1 only adds tasks; existing tasks stay DONE. If new feature requires changing existing code, user starts a new project or waits for refactor support. | Document explicitly in design + UX. |
| **Task ID overflow** at high cycle counts (e.g. T-099, T-100 — formatting assumption breaks) | Low | Current padding is 3 digits (`T-001`). Project would need 99+ tasks to overflow; not realistic in single sessions. Add explicit cap-and-warn at T-999. | `runtime/orchestrator/task_dag.py` |
| **LockedStack drift across cycles** if a future bug allows it to mutate | Low | `LockedStack` is frozen dataclass + persisted as JSON read-only in stack.json. Add a regression test: any code path that touches stack.json after first lock must raise. | `runtime/architecture/locked_stack.py` (existing) |
| **HITL fatigue** when user does many small extends (G1 + G2 per cycle) | Medium | Acceptable trade-off — each cycle adds new decision surface; skipping HITL would re-introduce the bug class Phase 0 closed. If users complain after live use, consider an `--auto-approve` flag for trivial extends. | Defer. |
| **Audit log size growth** with many extend cycles | Low | Per-cycle audit volume is small (~10-20 events); 100 cycles = 1500 lines added to `decisions.jsonl`. Reasonable. | Defer. |

## 13. Open design questions for user review

These are decisions I made tentatively in §2 — call out any I should revisit before code starts.

1. **In-place delta vs sub-project (§2 row 1).** I picked in-place. Alternative: each extend cycle creates a child workspace `<id>-ext-<N>/` with a symlink to the parent. Cleaner separation but more user-facing complexity. **Defaulting to in-place unless you want to push back.**

2. **PRD/RFC append vs full rewrite (§2 row 2).** I picked append. Alternative: rewrite the whole PRD and RFC, marking deltas with `[ADDED-CYCLE-N]` comments. Better holistic view but harder to read history. **Defaulting to append.**

3. **HITL G1/G2 firing per cycle (§2 row 5).** I made them mandatory. Alternative: G1/G2 only on cycle 1; later cycles auto-approve if "trivial" (small delta, no new modules). Risky — what counts as "trivial"? **Defaulting to mandatory; revisit after live use.**

4. **Stack mutability (§2 row 3).** I locked it forever. Alternative: allow `key_libraries` to be amended via a separate command (`ortim stack add <id> <lib>`). Useful for "add an analytics lib" extends. **Defaulting to locked; add `ortim stack add` as a future item if needed.**

5. **Cycle numbering in audit (§2 row 8).** I added new event types (`extend_initiated`, etc.). Alternative: reuse existing event types with a `cycle: int` field. The new-type approach is more grep-friendly but adds schema surface. **Defaulting to new event types.**

6. **Drift detection scope (§2 deferred bucket).** Out of M3.1. But should it be M3.1.2 immediately, or wait for actual user reports of drift? **Defaulting to wait for reports.** Currently the workspace is fully managed; manual edits are rare.

7. **`ortim extend --status` design (§6).** I sketched it. Question: should this be a sub-command (`ortim extend <id> --status`) or a top-level command (`ortim extensions <id>`)? The latter reads better. **Slight preference for `ortim extensions <id>`** — call out if you want the sub-command form.

8. **First proof-point feature for M3.1.1 E2E (§8.10).** "Add tagging to tasks" assumes the v4 todo. Realistic delta brief examples to validate against: tagging, due-dates, priorities, archive-action, bulk-delete. Pick one as the canonical M3.1 demo. **Defaulting to tagging** (most common feature add for todo apps).

Answer the above (or "all defaults are fine, lock it") and I'll proceed to M3.1.0 implementation.
